# AGENTS.md — bot-farm

Главный Telegram-бот `@` (см. `BOT_TOKEN` в `.env`, не печатать секрет), который
управляет парком других ботов: владелец шлёт `.txt` со списком токенов, для
каждого поднимается дочерний бот, копящий аудиторию и отвечающий заданным
текстом на любое личное сообщение.

## Код

- `app/main.py` — точка входа: поднимает главного бота + всех сохранённых
  активных дочерних ботов из БД, запускает их параллельно в одном процессе.
- `app/manager.py` — `BotManager`: добавление бота по токену (валидация через
  `getMe`), запуск/остановка/удаление, доступ к `Bot`-инстансу дочернего бота
  (нужен для `/broadcast`). Перед `start_polling` для каждого бота дергает
  `bot.delete_webhook()` — часть токенов из внешних источников приходит с уже
  настроенным webhook'ом, без снятия которого `getUpdates` падает с
  `TelegramConflictError`. Каждому дочернему `Dispatcher` — свой `Router`
  (`child_handlers.build_router()`): один `Router`-объект нельзя подключить
  сразу к нескольким `Dispatcher`, аiogram кидает `RuntimeError` на втором
  `include_router` — это всплыло только при одновременном запуске сотен ботов,
  не при одном.
- `app/main_handlers.py` — команды владельца (`OWNER_ID` из `.env`): приём
  `.txt`, `/list`, `/settext`, `/setall`, `/stats`, `/remove`, `/broadcast`.
  Все хэндлеры игнорируют не-владельца молча.
- `app/child_handlers.py` — единственный хэндлер для всех дочерних ботов:
  ловит любое личное сообщение, пишет пользователя в `audience`, отвечает
  текстом для этого бота (или `DEFAULT_REPLY_TEXT`).
- `app/storage.py` — `aiosqlite`, `data/bots.sqlite3`: таблицы `bots` и
  `audience`. Текст ответа хранится в БД и читается на каждое сообщение —
  `/settext` применяется без рестарта.

## Деплой

Живёт локально на Windows-машине kiro-bot (не на srv1/srv2), под своими
задачами планировщика — владелец дал разрешение их завести:

- `BotFarm` — `pythonw run.py` при логоне пользователя, `RestartCount 999`
  (авторестарт средствами Task Scheduler).
- `BotFarmWatchdog` — каждые 2 минуты запускает `watchdog.ps1`, который
  проверяет, жив ли процесс (`*app.main*` в командной строке), и если нет —
  включает и стартует `BotFarm`. Лог: `watchdog.log`.
- Переустановка после правок кода: `Stop-ScheduledTask BotFarm` → убить
  оставшийся процесс (`pythonw ... run.py`) → `Start-ScheduledTask BotFarm`.
- Основные логи бота: `bot-farm.log` (ротация, `RotatingFileHandler`,
  5 МБ × 2 бэкапа) — под `pythonw` консоли нет, весь вывод идёт только сюда.

Это отдельные задачи от `KiroBot`/`KiroBotWatchdog` — их не трогают и не
ломают. Юнит для systemd (`deploy/bot-farm.service`) оставлен на случай, если
бота вместо этого решат перенести на srv1/srv2 — процедура в `README.md`.

Секрет `BOT_TOKEN` в `.env` (в git не коммитится, см. корневой `.gitignore`)
— не печатать и не копировать в ответы.

## Источник токенов

`project/_ops/bot_farm_import_dorv_tokens.py` — разовый скрипт, которым
импортировали токены из `Desktop\супер дорвеи\dorv\token.txt` +`token2.txt`
(вне репозитория, папка отдельного инструмента для обновления профиля ботов и
ручной рассылки). Проверяет каждый токен через `getMe`, живые сохраняет в
`bots.sqlite3` без текста ответа (владелец задаёт его сам через `/setall` или
`/settext`), мёртвые (`401 Unauthorized`) пропускает. Запускать при
остановленной задаче `BotFarm`, потом перезапустить задачу, чтобы
`manager.start_all()` поднял добавленных ботов.
